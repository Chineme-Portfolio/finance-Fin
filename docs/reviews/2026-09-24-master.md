**Verdict**: Blocked

## Summary

F3, the match differential engine, is well structured and mostly honors the two load-bearing invariants (never assert absence of a match; never assert a dollar figure while unsure one exists). Types, wiring, purity, and determinism are solid, and the fixture suite is broad. However, the pairing heuristic in `groupByDate` has a concrete, reproducible bug: a single ambiguous deposit line can be read as an itemized employer+employee *pair* and have its own amount double-counted into both sides of the ratio, producing a fabricated 100%-match reading and — once a formula and gross pay are known — a fabricated positive `unclaimed.amountMinor`. That is exactly the class of error §7 #16's mirror rule exists to prevent, so this blocks merge. A second, narrower issue: the `below_match_threshold` cause (the actual "you're leaving money on the table" finding) has zero direct test assertions anywhere in the suite, despite being the highest-value and highest-risk cause in the differential.

## Blockers

### 🔴 A single ambiguous deposit line is read as a paired 100% match, which can produce a fabricated dollar figure, `lib/insights/match-differential.ts:114-125`

**Problem**: `groupByDate` computes `hasDeferral` and `hasMatch` independently via `dayEvents.some(...)` over the *same* set of events for the day, without requiring the two hints to come from distinct events. `itemized = hasDeferral && hasMatch` (line 122) is therefore `true` even for a **single** event whose `rawName` happens to contain both a `DEFERRAL_HINTS` substring (`"employee"`, `"deferral"`, `"elective"`, `"pre-tax"`, `"pretax"`) and a `MATCH_HINTS` substring (`"employer"`, `"match"`, `"matching"`) — e.g. a line literally named `"EMPLOYEE MATCH"`. When `buildObservation` computes the ratio (lines 195-203), both the `deferral` sum and the `match` sum are filtered from the *same* one-event group, so the single deposit's amount is counted on both sides of the ratio: `observedRatioBps = round(amount * 10000 / amount) = 10000` (100%), regardless of the actual amount.

Verified by reproduction (`deriveMatch(acct, [{ ...rawName: "EMPLOYEE MATCH", amountMinor: 100000 }], facts(), null)`):
```json
{ "observation": { "pairing": "paired", "observedRatioBps": 10000 },
  "hypotheses": [{ "cause": "match_detected", "rank": 1, "signal": "ratio_below_headline" }, ...] }
```
And with a resolved formula + gross pay supplied (the same single ambiguous deposit, `contributionRateBps: 300`, `generic-tiered-safe-harbor`):
```json
"unclaimed": { "formulaId": "generic-tiered-safe-harbor", "amountMinor": 100000, ... }
```
One deposit, with no second line ever observed, produces a confident `match_detected` and a $1,000 "you're leaving this on the table" figure.

**Why it matters**: This is the false-positive mirror of foundation §7 #16 — stating a dollar figure while there is no real evidence a match exists at all (one ambiguous line is not two paired deposits). The whole design of this engine (ranked differential, gating on `hypotheses[0]`, the unclaimed gating rule) exists specifically to prevent a confidently wrong claim like this one. `EMPLOYEE MATCH`-style naming (a single line describing an employee's matched contribution) is a plausible real provider string, not a contrived one, and the hint lists were explicitly chosen without having observed real Northwind data (the whole slice is PROVISIONAL by design) — which makes guarding against exactly this kind of coincidental overlap more important, not less.

**Suggested fix**: Require the deferral hint and the match hint to come from **two different events** before calling a day `itemized` (e.g. `dayEvents.some(deferralHint) && dayEvents.some(matchHint) && dayEvents.length >= 2`, or track which specific event satisfied which hint and require they differ). Add a fixture with a single ambiguous line to the suite once fixed, so this can't regress silently.

## Major

### 🟠 `below_match_threshold` — the differential's actual "real finding" — has no direct test assertion anywhere in the suite, `lib/insights/match-differential.test.ts`

**Problem**: `below_match_threshold` is one of the seven `MatchCause` values and, per the spec's own framing (index.md AC-2, AC-11, rationale.md), it is *the real finding* — the one case where the tool should say something is actually being left unclaimed for a reason within the user's control. Searching the test file for the string `below_match_threshold` returns zero hits. The "positive detection + unclaimed" test (`match-differential.test.ts:109-126`) exercises the code path indirectly (it sets `contributionRateBps` below the cap so `belowCap` is `true`), but never asserts that `below_match_threshold` actually appears in `hypotheses`, at what rank, or with what signal — it only checks the resulting `unclaimed` figure. The `pairing === "single"` branch's own `below_match_threshold` push (`match-differential.ts:247-249`, i.e. an unpaired stream where the user's stated contribution rate is below a *resolved* formula's cap) is completely unexercised: no test combines `singleEvents(...)` with a non-null `formulaEntry` and a `contributionRateBps` below the cap, in either the `windowSufficient` or not-`windowSufficient` case.

**Why it matters**: This is exactly the branch that governs whether `unclaimed` gets populated for the *unpaired* stream (via `matchSupported` and `matchObservedOrWindowSufficient` in `deriveMatch:346-394`), i.e. the highest-consequence money-bearing branch in the file, per code-standards §8 ("the rule that decides all of it: if being wrong here would show a user an incorrect dollar figure, it is tested"). Right now nothing pins its rank, its interaction with `windowSufficient`, or that it actually gates the dollar figure correctly in the unpaired case (as opposed to only in the paired case, which the existing tests do cover).

**Suggested fix**: Add cases for `singleEvents(...)` + a resolved formula + `contributionRateBps` below cap, covering both `windowSufficient: true` and `false`, asserting `below_match_threshold`'s presence/rank and whether `unclaimed` is populated in each.

## Minor

### 🟡 `monthsBetween` can overstate the window by up to ~1 month at day-of-month boundaries, letting `windowSufficient` flip true just under the real 13-month floor, `lib/insights/match-differential.ts:61-69`

**Problem**: `monthsBetween` computes `(b.year - a.year) * 12 + (b.month - a.month)`, ignoring day-of-month entirely. For an earliest date late in a month and a latest date early in a later month (e.g. `2025-01-31` → `2026-02-01`, a real elapsed span of ~12.03 months), this yields `windowMonths = 13` (`(2026-2025)*12 + (1-0) = 13`), satisfying `SUFFICIENT_WINDOW_MONTHS`.

**Why it matters**: `windowSufficient` directly gates `matchObservedOrWindowSufficient` in the unclaimed rule, and AC-4/the build-graph's "≥13 month requirement" is exactly the guard against concluding too early that an annual lump-sum match has been ruled out. The overstatement is bounded (under one month), so this is a boundary issue rather than a gross one, but it means the ≥13-month floor is not actually enforced at the boundary — a window that is really ~12 months can be treated as satisfying a 13-month requirement.

**Suggested fix**: Compute the span in days (or fractional months) rather than calendar-field subtraction, or explicitly document that whole-calendar-month semantics intentionally rounds in the direction that must never be optimistic (round down / floor, not up).

### 🟡 `observation.observedRatioBps` can be `null` even when `pairing === "paired"`, contradicting its own doc comment, and `buildHypotheses` has no explicit branch for that combination, `lib/types/domain.ts:201`, `lib/insights/match-differential.ts:183-204,230-255`

**Problem**: `pairing` is set to `"paired"` whenever `paidGroups.length > 0` (`match-differential.ts:184`), but `observedRatioBps` is computed only from the subset of `paidGroups` that are *not* true-up-flagged and have `deferral > 0` (`188-203`); `modeOf([])` returns `null`. If every itemized pair happens to be excluded (e.g. the only itemized date found is also flagged `true_up_correction`), the result is `pairing: "paired"` with `observedRatioBps: null` — a combination the type's own doc comment rules out ("Null when no itemized pair was found," `lib/types/domain.ts:201`). `buildHypotheses`'s first condition (`match-differential.ts:230`) requires *both* `pairing === "paired"` **and** `observedRatioBps !== null` to take the paired branch, so this combination silently falls through to the `else` (single-stream) branch's logic — logic that was written for genuinely unpaired data — even though the observation is, per its own `pairing` field, `"paired"`.

**Why it matters**: Low likelihood (needs every itemized pair to be true-up-flagged or have zero deferral), but it's a real reachable inconsistency between a field's documented contract and its actual behavior, and it means the ranking logic silently reuses the wrong branch for a case it wasn't designed for.

**Suggested fix**: Either fix the doc comment to state the true contract ("null when no itemized pair *contributes to the ratio*, which can happen even when `pairing` is `\"paired\"`"), or add an explicit `pairing === "paired" && observedRatioBps === null` branch in `buildHypotheses` so the fallthrough is intentional rather than incidental.

### 🟡 No `MatchQuestion` code exists for a missing `contributionRateBps`, so the unclaimed gate can silently stay closed with no question telling the user what's missing, `lib/insights/match-differential.ts:282-320,371-394`

**Problem**: The unclaimed gate (`deriveMatch:371-379`) requires `formulaEntry`, `atCapContributionBps`, and `planFacts.contributionRateBps` **and** `planFacts.grossPayMinor` all to be non-null. `buildQuestions` asks for a missing formula (`recognize_formula`) and a missing `grossPayMinor` (`provide_gross_pay`), but there is no question code, and no check, for a missing `contributionRateBps`. If `contributionRateBps` is `null` while a formula and gross pay are present, `unclaimed` stays `null` (correctly, per the gating rule) but nothing in `questions` says the current contribution rate is the missing input — the user only sees confidence-type questions (e.g. `confirm_ratio_looks_like_match`) with no indication of *why* no dollar figure appeared.

**Why it matters**: AGENTS.md's non-negotiable #4 ("never render a blank or zero for missing data — explain what can't be seen," foundation §4 #7) is about explaining absence; here the absence (`unclaimed: null`) is correct but unexplained for this specific missing input, since `questions` doesn't name it.

**Suggested fix**: Add a `provide_contribution_rate` (or similarly named) `MatchQuestion` and push it when `planFacts?.contributionRateBps == null`, mirroring the existing `provide_gross_pay` check.

## Nits

## Strengths

- The gating structure itself (`hypotheses[0]` always travels with the Insight; `unclaimed` requires both the money inputs *and* `matchSupported` *and* `matchObservedOrWindowSufficient`) is a genuinely careful reading of the spec's false-positive mirror rule, and the AC-12/AC-5 gating-both-ways tests do verify it correctly for the tested (paired and blended) cases.
- The AC-9 purity test (`match-differential.test.ts:308-324`) statically greps the module's own source for forbidden imports and mutation — a nice, cheap enforcement of the module boundary that will catch regressions eslint/tsc wouldn't.
- True-up exclusion from the ratio (AC-7) is correctly implemented and tested for the realistic "outsized deposit at the end of the window" case.
- Every heuristic threshold carries a comment citing its provisional status and source per code-standards §9, and the module-level doc comment is unusually clear about what is and isn't guaranteed.
