## Major

### 🟠 `Stat`'s count-up never updates a non-animated value after mount, `components/ui/Stat.tsx:16-20`
**Problem**: `useCount(target, run)` seeds state with `useState(run ? 0 : target)` — a one-time initializer — then the effect's only escape hatch when `!run` is an early return (`if (!run) return;`, line 19) that never calls `setN`. On mount this is harmless (initial state already equals target). But if a `Stat` with `animate` unset (the default, and what every account-total and gapped-balance `Stat` on this screen uses) re-renders with a **different** `value` prop later, `n` is never updated — the effect runs (target/run are in the dependency array) but takes the `!run` branch and does nothing, so the component keeps rendering the old number.
**Why it matters**: This screen's Server Component render never changes props post-mount, so the bug is silent today. But `Stat` is registered as "the primary way money is shown" for every future screen (`ui-registry.md`), and spec 0003's own Follow-up is "replace the static view model with a live source" — the very next slice will have account totals and balances that change after the initial render (revalidation, live fetch) while `animate` stays unset for anything but the one hero figure. When that lands, this bug reproduces as a stale dollar figure on screen with no visual indication anything is wrong — the exact failure class `foundation.md` §4 #1 calls out as trust-destroying.
**Suggested fix**: In the `!run` branch, call `setN(target)` (or drop the early return and always land on `target` outside the animated path) so a prop change is always reflected, not just the initial mount value.

### 🟠 `lib/view/what-you-own.ts` branching logic has no test coverage
**Problem**: `loadWhatYouOwn` and `portfolioTotalMinor` contain the screen's real decision logic — which account gets its `holdings` capability stripped, which accounts are shown vs. dropped (`shown = views.filter(v => v.holdings.length > 0 || !v.seesHoldings)`, line 111), and how the cross-account total is computed differently for capability-gapped vs. holdings-visible accounts (lines 53-59). None of it has a test, and no test file exists for this module or for `lib/format.ts`.
**Why it matters**: Test signal is `configured` (Vitest, with `lib/insights` and `lib/aggregator/plaid/map` already covered by the same convention), and `code-standards.md` §8 says exactly this kind of code — pure, branching, money-figure-producing — is "cheap to test" with "no excuse." The filter that drops the empty HSA and keeps the gapped 401k, and the total that has to fall back to `balanceMinor` for one branch, are precisely the kind of logic that silently breaks when the fixture or the aggregator mapping changes upstream, and nothing here would catch it.
**Suggested fix**: Add `lib/view/what-you-own.test.ts` covering: the gapped-401k path (capability stripped, balance still present, holdings empty), the empty-HSA-is-dropped path, and `portfolioTotalMinor` for both a holdings-visible and a gapped account. `lib/format.ts` is lower-risk but still new, worth a handful of cases (zero, gapped `null`, rounding).

## Minor

### 🟡 `portfolioTotalMinor` re-derives an account total the engine already computed, `lib/view/what-you-own.ts:53-59`
**Problem**: For holdings-visible accounts, `portfolioTotalMinor` recomputes `sum of positive-valued holdings` inline (`h.valueMinor > 0 ? h.valueMinor : 0`) instead of reading `accountTotalMinor` off the composition `Insight` that `loadWhatYouOwn` already derived for that same account (`view.insights`). `lib/insights/shared.ts`'s `holdingsTotalMinor`/`positiveHoldings` exist specifically, per their own comment, "so the account-total definition... has a single source of truth, rather than being recomputed in each insight and drifting" — and this is exactly that recomputation, just one layer up.
**Why it matters**: Today the two calculations agree (verified against the fixture). If the engine's definition of what counts toward a total ever changes (e.g., a future invariant excludes another holding class), this helper won't move with it, and the portfolio header total could silently disagree with the sum of the per-account `Stat`s directly below it on the same screen — an internally inconsistent number, which is the thing `foundation.md` §4 #3 (traceability) exists to prevent.
**Suggested fix**: Where `seesHoldings` is true, pull the total from `compositionOf(view.insights)?.accountTotalMinor` (falling back to 0 only if composition is genuinely null) rather than re-summing holdings.

### 🟡 Unvalidated double cast on the fixture read, `lib/view/what-you-own.ts:42-46` and `:77-82`
**Problem**: `readFixture()` does `JSON.parse(...) as { data: RawHoldingsResponse }` with no runtime check, and `loadWhatYouOwn` passes the result through a second `as Parameters<typeof mapHoldingsResponseToDomain>[0]` cast. Neither validates the fixture actually has the shape claimed.
**Why it matters**: `code-standards.md` §2 requires boundary data to be "validated into a known type at the edge." If the committed fixture is ever hand-edited, regenerated in a different shape, or the `data` wrapper key changes, `raw.accounts` throws `Cannot read properties of undefined`, which crashes the whole page with a raw Next.js error rather than the graceful, explained-gap behavior `code-standards.md` §6 asks for elsewhere in this codebase. Low likelihood (it's a single committed, controlled file) but a real gap against the stated standard, and the double `as` is exactly the kind of cast that "hides a real shape mismatch" if one is ever introduced upstream.
**Suggested fix**: A small runtime guard (even just checking `parsed?.data?.accounts` is an array before proceeding, with a thrown, context-prefixed error per §6) would turn a silent crash into an honest one.

### 🟡 `HoldingRow` list is unfiltered while the allocation total excludes non-positive holdings, `app/page.tsx:102-113`
**Problem**: `AccountView.holdings` (used for the `HoldingRow` list) is every holding tied to the account with no filter; `AllocationBar`'s segments and the account-total `Stat` come from the composition `Insight`, which explicitly excludes holdings with `valueMinor <= 0` (`lib/insights/composition.ts`, `positiveHoldings`) and tracks how many via `excludedCount`. `excludedCount` is never read anywhere in `app/page.tsx`.
**Why it matters**: Not triggered by the current fixture (verified: no zero/negative-value holdings in `fixtures/holdings-ymw6pgkb.json`), so nothing is visibly wrong today. But if live data (or a future fixture) ever includes a written-down or zero-value position, the screen would render a `HoldingRow` for it while the allocation bar and total silently exclude it — numbers that don't add up with no explanation, which is the opposite of `foundation.md` §4 #3's traceability guarantee.
**Suggested fix**: Either filter the row list to the same positive-holdings set the engine used, or surface `excludedCount` as a short caption when it is nonzero.
